Part A — Questions

Question 1

What is Infrastructure as Code, and which problems of manually created infrastructure does it solve? Use your own Week 1 VM setup as an example.

It is a DevOps practice that consists of managing and provisioning computing resources (like servers, networks and databases) through configuration files that machines can read, instead of doing physical or manual configurations. When IT teams configure servers by hand (clicking through web panels or running separate commands in terminals), they face serious problems that IaC directly helps solve, such as configuration drift, human errors and lack of documentation, slow deployments and lack of scalability, and no clear history or audit trail.

In Week 1 I did practically the same thing as this week, but using two different methods. In Week 1 I configured the machine from the web interface and did everything step by step manually. To create another VM I would have needed to repeat all the steps again. I installed Apache on the virtual machine through SSH and configured the SSH and HTTP rules manually.

Question 2

Explain the difference between declarative and imperative infrastructure automation. What does idempotency mean, and why is it important?

The main difference between declarative and imperative infrastructure automation is how the final state of the resources is defined. With the declarative approach, you define what you want to get (the final result), and the tool decides how to do it. With the imperative approach, you define how to reach that result step by step (the commands that need to be run).

Declarative approach: You write a configuration file that simply says: servers: 3. If the system detects that there is already 1 server running, it will create only the 2 missing ones. If there are already 3, it will do nothing.

Imperative approach: You write a script that says: 1. Log in, 2. Create server A, 3. Create server B, 4. Create server C. If you run this script twice by mistake, it could try to create another 3 servers, causing duplicates or errors.

Idempotency is a property of some operations that means you can apply them several times and get exactly the same final result as applying them once. Doing an action once or repeating it five times gives the system the same final state.

Idempotency is important because it makes retries after failures easier, helps avoid unwanted repeated changes, and simplifies automation.

Question 3

What is the state file used for? Why should it not be committed to a Git repository, and how do teams usually share it instead?

The state file is a file OpenTofu uses to keep track of the infrastructure resources it manages. It is important to protect it because the state file can contain sensitive information, such as passwords, tokens or configuration values. If several people work on the same project, the usual solution is to use remote state, which means storing the state in a shared and protected system. It is also important to have state locking, which prevents operations on the same state at the same time when the backend supports it.

Question 4

What is configuration drift, how does it happen, and how does an IaC tool detect it?

It is the gradual and unplanned change in the configuration of a system, server or network that makes it move away from its original, approved or ideal state. The main causes are manual changes or quick fixes, automatic updates, differences between environments and lack of version control. It happens when the real state of your cloud infrastructure no longer matches the desired state defined in your code files.

IaC tools (like Terraform, AWS CloudFormation or Pulumi) can detect drift by comparing information from the saved state with what actually exists in the cloud and what the configuration says should exist. This involves refreshing the real state and comparing the differences.

Part B — Hands-on: Rebuild the VM as Code

1. Introduction — Objective of the practical exercise

The goal of this practical exercise was to create cloud infrastructure automatically using OpenTofu. We used CSC cPouta, which is based on OpenStack, and then created an Ubuntu virtual machine with Apache. I automatically configured the network connection, firewall rules, SSH key and public IP address. We used cloud-init to install Apache and create the HTML page without doing it manually. Finally, I did three experiments to understand how OpenTofu manages infrastructure.

2. Infrastructure Setup

2.1. Tools and technologies

To build this whole environment I combined several tools that complement each other. The base of my work was OpenTofu version 1.13.0, which I used as an Infrastructure as Code tool to define and create resources without having to create them by hand. All that infrastructure lives in CSC cPouta, which runs on OpenStack and is where I created the virtual machine. From my own computer I used the PowerShell terminal to write and run the commands. Inside the virtual machine I chose Ubuntu 24.04 as the operating system, and on top of it I installed Apache so it could work as a web server and show the site. To avoid having to log in and configure the machine as soon as it started, I used cloud-init, which took care of setting everything up automatically on the first boot. Finally, I uploaded the code to a GitHub repository to have a clear and organized record of the changes.

2.2. Project files

I organized the project into several files so that each one had a specific role. The heart of my deployment is main.tf, where I tell OpenTofu exactly which infrastructure resources I want to create. In versions.tf I specified that I would use OpenStack and which provider version I needed. To make the code flexible, I used variables.tf to declare the project parameters, while in terraform.tfvars I put the real values I wanted to use for my case. When the infrastructure is created, outputs.tf shows useful data in the terminal, such as the public IP, website link and machine name. I handled the operating system part with cloud-init.yaml, which contains the instructions to update Ubuntu, install Apache and create the home page. To keep my repository clean and safe, .gitignore prevents temporary files or sensitive data from being uploaded, while .terraform.lock.hcl locks the selected provider versions so they stay consistent. Also, to connect to CSC I used Application Credentials saved in a clouds.yaml file outside the repository, protecting my access keys.

2.3. Deployment process

When creating the infrastructure, I followed the usual process with OpenTofu commands. I started with tofu init to prepare the folder and download the necessary providers. Then I ran tofu validate to check that my configuration was valid and had no syntax problems. The key step before touching anything in the cloud was tofu plan, which showed me a preview of which resources would be created or changed. Once I checked that everything looked right, I ran tofu apply, which actually created everything in cPouta. Finally, I used tofu output to see the IP address and access details in my terminal. In practice, the process created the seven resources and I could open the Apache website from the browser, which I checked with screenshots of the initial deployment and the working website.

3. Experiment 1 — Infrastructure Changes

3.1. Change 1 — Security group description

My first experiment was quite simple: I went into main.tf and changed only the description text of the security group. My prediction was that OpenTofu would just change that text without touching the rest of the resource. When I ran the plan I saw that it showed zero resources to add, one to change and zero to destroy, doing an in-place update. This happened because OpenStack allows changing the description of a security group without needing to delete it or recreate its rules, so my prediction was correct.

3.2. Change 2 — Virtual machine name

In my second test I changed the name of the virtual machine in the code, from cloud-week7-vm to cloud-week7-vm-test. In this case I imagined that OpenTofu would destroy the machine and create a new one from scratch to give it the new name. However, the result surprised me: the plan again showed that it would only change one resource in place, without destroying anything. My prediction was wrong because I assumed the name was fixed, when actually OpenStack allows renaming a running machine without reinstalling it or losing what is inside.

3.3. Change 3 — SSH key pair name

For the third change I modified the SSH key pair name from cloud-week7-key to cloud-week7-key-new. I predicted that OpenTofu would replace the key pair, but the plan showed that it would add two resources and destroy two. So it would not only replace the key pair, but the whole virtual machine too. This is because the SSH key pair is assigned when the machine is created; changing this association in our configuration forces a new machine to be created. When I saw that the change would destroy my machine unnecessarily, I decided not to apply it and put the code back as it was before.

3.4. Conclusion

These three tests taught me some very clear things. First, I understood that there are properties I can edit directly without a problem, while others force a resource to be destroyed and created again. Second, I saw how easy it is to create a domino effect: touching a basic resource like the SSH key pair can end up deleting the machine that depends on it. Because of all this, using tofu plan before every apply is an essential habit I started using, since it warns me in advance if I am about to delete something important by mistake.

4. Experiment 2 — Configuration Drift

4.1. Manual modification

The goal of this experiment was to see what happened if I made changes outside the code. I went directly into the CSC cPouta website, looked for the security group and changed its description manually from the graphical panel, leaving the main.tf file untouched on my computer.

4.2. Prediction

My idea was that OpenTofu would immediately notice that what was in the cloud no longer matched what my file said, and that it would propose overwriting that manual change to return to what I had written in the code.

4.3. Result

When I ran tofu plan, I confirmed what I thought: OpenTofu checked the cloud, saw the difference in the description and told me that there was a pending change to fix it in place. When I ran tofu apply, it automatically restored the original text I had in main.tf and left everything matching again.

4.4. Reflection

This situation is what is known as configuration drift. It happens a lot when quick changes are made from the web console or quick fixes are applied without going through the code, which makes reality start moving away from what is documented. I could check that OpenTofu handles this by comparing the real cloud resources with its state file and my code, bringing things back to the declared configuration. But I also understood it has limits: OpenTofu watches the cloud resources it manages, but it does not normally know if I enter the machine through SSH and manually change a line in an Apache configuration file.

5. Experiment 3 — Destroy & Rebuild

5.1. Prediction

In this last test I wanted to check if I really could rebuild everything from scratch using only my code. I predicted that after deleting everything the website would stop working, but that when I applied the code again the machine would start on its own, cloud-init would install Apache again without anyone helping, and the public IP address would probably change because the cloud would give me a different one.

5.2. Destroy

First I ran tofu plan -destroy to make sure what would be deleted, confirming that it affected the seven resources. Then I ran tofu destroy to clean everything up and, when I checked with tofu state list, I saw that the list was completely empty, confirming that no managed resources were left in OpenTofu state.

5.3. Rebuild

With the resources removed, I only needed to run one command: tofu apply. OpenTofu recreated the network port, keys, rules and virtual machine using the project network that already existed. When the system started, cloud-init did its job in the background, installed Apache and left the website ready to be visited, all without me having to enter through SSH or configure anything by hand.

5.4. Results

When I compared before and after, I saw that the machine kept exactly the same name and the website worked again automatically. The real difference was the public IP address, which before was 86.50.20.216 and afterwards was 86.50.20.144, just as I had expected in my prediction.

5.5. Reflection

The test confirmed that my prediction was correct. The IP changed because when I destroyed the infrastructure I released the old address back to the cloud pool, and when I requested a new one I received another available address. This showed me the real power of Infrastructure as Code: if one day my server breaks or I need to copy the environment for testing, I can recreate it from the same code in a few minutes. But one critical thing became clear to me: rebuilding the machine does not recover files or data that were stored inside it, so databases and important information need persistent storage or independent backups.

6. Comparison — Manual vs. Automated Deployment

The difference between what I did in Week 1 and what I achieved in Week 7 is huge. At the beginning I created the machine by clicking through the CSC website, added firewall rules one by one by hand and had to connect through SSH to write the commands to install Apache. If something went wrong or I wanted to do it again, I had to remember every step and repeat the whole process, with the constant risk of getting a detail wrong. Also, I made adjustments directly in the panels without a clear record of what I had changed.

With OpenTofu my way of working changed completely. I have all the infrastructure written in text files that I can save on GitHub, review calmly and version. The rules and the machine are created from my code, cloud-init takes care of installing the software without me doing it manually, and if I want to rebuild the whole environment I only need one command. Of course, getting started with Infrastructure as Code took a learning curve: at first it was difficult for me to understand the declarative logic, how resources relate to each other and how the state file works. But once I got past that, I gained a sense of calm, speed and organization that makes me not want to go back to creating servers by hand.
